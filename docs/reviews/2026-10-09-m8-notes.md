## Blocking finding

**B1. A symlinked data directory is written through, and its target is chmodded** (`src/server/local-store.ts:203–206`, `#write`).

- **What's wrong:** if the app data directory is itself a symlink to a directory outside the project, `mkdir(..., { recursive: true })` succeeds on the existing link. `chmod(dir, 0o700)` then follows the link and changes the target's mode, and the notes file is written inside the target.
- **Probe result:** enable 200, create 200; `notes-<key>.json` was written in the target; the target's mode became `40700`.
- **Why it blocks:** the brief says the store must not write through a symlink to elsewhere. A target repo can't create this link, so exploitability is low.
- **Fix:** before `mkdir`/`chmod`, `lstat` the data directory's final component. If it exists and is a symlink or not a directory, refuse with a sanitized code and write nothing. Never `chmod` a path that could follow a link. Add a test.

Already safe: a data dir symlinked into the root, a symlinked parent pointing into the root, a dangling data-dir link, and a notes file replaced by a symlink.

## Non-blocking notes

1. **Editing or deleting an unknown note ID rewrites the file before returning 404** (`src/server/project-notes.ts:136–153, 160–166`). The content is unchanged, but a 404 should write nothing. Found by code reading.
2. **Consent can't be revoked in the app.** "Turn notes off" lasts for this launch only, and "Delete all notes" keeps the file, so notes turn back on at the next launch. Document the manual step.
3. **The moved-lines search is slow on hostile files** (`src/server/note-status.ts:88`). A 100,000-line file where the head line repeats everywhere took 1,392 ms for one 200-line note; all-identical lines took 203 ms. This stays within the 1 MiB file cap. A per-request memo would bound it.

5. **Panel tests are static renders only.** Browser behavior is unverified.
6. **A failed read stays failed for the whole launch,** even after a transient error. This is disclosed.
