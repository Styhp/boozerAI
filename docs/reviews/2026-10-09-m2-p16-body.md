## Code review

- `explanationBody` (`project-api.ts:37–53`) reuses `fields()`, so every accepted field is a non-empty string and the key count is exact. A hash without `provider: 'cloud'`, `provider: 'local'` with a hash, and `provider: null` or `'Cloud'` all fail with `invalid-body`. The tests cover each case.
- `session.beginExplanation` still validates the snapshot and path before the service runs. The 120 s route timeout, backpressure and refresh/close cancellation are unchanged and apply to cloud requests too.
- With no provider, the service request has no `provider` or `previewHash` property, so the local path is byte-for-byte the earlier call (tested).
- The ARCHITECTURE.md route row matches the code.

## Non-blocking notes

- **N1. The preview hash is a checksum, not proof that someone saw the preview.** It is SHA-256 of the exact payload, so it stops a payload changing between preview and send. Anyone holding the launch capability could compute it, because the source and the prompt are both readable. Only the user's own browser holds that capability, and no client sends cloud requests yet, so this is acceptable for this slice. When the preview route and UI land, consider a server-issued, single-use preview ID so the server knows a preview was actually issued.
- **N2. The route is reachable for cloud whenever `OPENAI_API_KEY` is set at launch.** `app.ts` creates the OpenAI adapter by default. For the offline demo, launch without the key unless the comparison is part of the shot.
- **N3. Response shape.** Body errors return HTTP 400 JSON. Service errors such as `preview-mismatch` arrive as HTTP 200 with one NDJSON error event, the same as existing explanation errors. The future cloud UI must handle both.
